# 后端运营后台（backend）接口与数据契约审计报告

> 审计对象：`backend/`（Vue 3 + Element Plus + Pinia + vue-router + axios + MSW Mock）
> 审计范围：`src/api`、`src/types`、`src/constants`、`src/stores`、`src/router`、`src/layouts`、`src/composables`、`src/components/business`、`src/mocks/{db,domain,handlers,seed}`、`src/views`
> 审计方式：逐文件静态比对「页面调用 → api 方法 → HTTP 端点 → MSW handler → domain 规则 → seed 数据 → 权限」全链路，不运行、不猜测。
> 结论标记：**✅ 一致** / **⚠️ 偏差** / **❌ 未实现** / **❓ 待确认**
> 落地状态标记（据第八、九节与本次实现回填）：**✅ 已落地** / **🟡 部分落地** / **⏳ 待后端接入** / **⏳ 待确认**
>
> **说明**：第一至第五节为本报告的**修复前基线审阅**（保留原判定以体现问题来源）；本轮优化实现后的最新状态以第六节「落地状态」、第八节「落地状态」列与第九节勾选为准。本仓库无 Java 服务端，「后端实现」以前端契约层（DTO/类型/权限码/错误码）+ MSW handler/domain 真实行为为准，凡必须依赖真实后端的项（签名 token 会话、支付渠道真实回调、分布式调度）如实标注「⏳ 待后端接入」。

## 一、结论摘要

1. **接口覆盖完整**：前端所有 `api/*` 调用的 `/api/admin/**` 端点在 MSW handlers 中**均有实现**，不存在「前端依赖但后端未提供」的接口。
2. **契约基本自洽**：请求参数、响应字段、分页结构（`PageResult{items,total,page,pageSize}`）、枚举、错误码在类型层与 handler 层**总体一致**，可支撑当前 Demo 页面渲染。
3. **存在 6 项实质性缺口**（详见第六节），其中最高优先级为：**大额积分调整审批只有「创建/展示」没有「通过/驳回」接口**、**积分冲正（撤销）只有文案没有接口**、**读接口普遍缺少权限校验**、**错误/状态码语义单一（一律 400）**、**RBAC 依赖可伪造的请求头且缺省放行**、**订单 KPI 前端聚合**。
   - **本轮落地情况（详见第六/八/九节）**：审批闭环、积分冲正、鉴权 fail-close+逐端点校验+真实操作人、状态码语义、后端聚合、权限码单一来源、技术债清理——均已 ✅ 已落地（契约/MSW 层）；异步副作用改集中化推进器+前端轮询、服务端真实回调与签名 token——🟡 部分落地（真实后端项标 ⏳ 待后端接入）。
4. **切换到 Spring Boot 的可行性：中高**。接口边界清晰、数据模型自洽、分页/幂等/状态机已在契约层体现，足以支撑前端功能落地；但迁移前必须先补齐第六节的鉴权、状态码、聚合口径、异步回调等契约约定，否则会出现「Mock 能跑、真后端语义不一致」的隐性断裂。

## 三、数据字段差异与风险清单

### 3.1 分页 / 响应包裹（一致项）
- `ApiResponse<T>{code,message,data,traceId}` 与 `client.ts` 拦截器 `isSuccessCode(code===0||'OK')` 完全对齐；handler 的 `ok()` 恒返回 `code:0`。✅
- 分页统一为 `PageResult{items,total,page,pageSize}`；`usePagedQuery` 仅读取 `items`/`total`。✅
- **非分页数组端点**（`getPlans/getAdmins/getRoles/getSystemHealth/getProviderHealth/globalSearch/dashboard/distribution`）直接返回裸数组，前端也按 `.data` 数组消费。⚠️ 真后端若统一加 `PageResult` 包裹会破坏前端；需在契约中固化「这些端点返回数组」。

### 3.2 `ListQuery.sortBy/sortOrder` 字段
- `types/api.ts` 定义了 `sortBy/sortOrder`，但 `paginate()` 与各 `page*` 函数**均未实现排序**，恒按 seed 顺序/时间。❓ 前端未暴露排序控件，属预留字段，真后端可暂不实现。

### 3.3 金额 / 积分类型
- 全部金额以 `*Minor`（分，整数）建模，前端 `formatMoney` 除 100；积分以整数。类型与 seed/handler 一致。✅
- `currency: 'CNY'|'USD'` 为联合类型，但 seed 与 `formatMoney` 仅覆盖 CNY/USD 展示，无 FX。✅（Demo 可接受）

### 3.4 字段命名差异（前端展示依赖 handler 派生字段）
| 派生字段 | 产生位置 | 消费页面 | 风险 |
|---|---|---|---|
| `CustomerUserListItem.organizationName` | `pageCustomerUsers` join | UserListView | 真后端需在列表 join 输出，否则「企业」列空 ❓ |
| `WorkflowListItem.userName/organizationName` | `pageWorkflows` join | WorkflowListView | 同上 ❓ |
| `OrderListItem.userName/organizationName` | `pageOrders` join | OrderListView | 同上 ❓ |
| `RiskEventListItem.contentTitle/userName` | `pageRiskEvents` join | RiskEventListView | 同上 ❓ |
| `JobDetail.attempts[]` | `getWorkflow/getJob` 内联 | WorkflowTimeline | 真后端需在详情内联 attempts ❓ |

> 以上均为「handler 侧聚合/连接出来的展示字段，不在基础实体类型里」。迁移 Spring Boot 时**极易遗漏**，应写入 DTO 契约。

### 3.5 枚举一致性核对
- `AdminRole`：`SUPER_ADMIN/OPERATIONS/RISK_REVIEWER/FINANCE`。`constants/permissions.ts`、`handlers/auth.ts` profiles、`seed createAuditLogs/role` 一致。⚠️ **但 `admin-architecture-spec.md` 描述为 `OPERATOR/REVIEWER`（旧命名）** —— 文档与代码漂移，以代码为准（`mocks/domain/permission-rules.ts`、`types/auth.ts`）。
- `Order.channel` 含 `WECHAT/ALIPAY/STRIPE/MANUAL_DEMO`；seed 仅用到 `STRIPE/MANUAL_DEMO`。✅（其余为未触发枚举，待确认支付渠道落地）
- `JobErrorCategory`（8 值）与 `job-rules` 用到的分类一致；`JobType`（9 值）与 seed 用到的 3 值一致，WorkflowListView 仅下拉 3 类。✅
- `ApprovalRequest.type` 含 `CAPABILITY_RESTRICTION`，但 `approvalQueue()` 只产出 `CREDIT_ADJUSTMENT` 与 `REFUND`。⚠️ 能力限制**不进入审批队列**（`updateUserCapabilities` 立即生效），该枚举分支为死约定。
- `CreditEntryType` 含 `PLAN_GRANT/PROMOTION_GRANT/REVERSAL` 等，seed/handler 仅使用 `JOB_CONSUMPTION/JOB_FAILURE_REFUND/PAYMENT_GRANT/REFUND_RECLAIM/MANUAL_CORRECTION/CUSTOMER_COMPENSATION`。⚠️ `REVERSAL`（冲正）**无任何写入路径**（见 6.2）。

### 3.6 硬编码操作人（贯穿 seed 与 domain）
- `credit-rules/risk-rules/billing-rules/job-rules/audit-rules` 中 `operatorId/requesterId/approverId/reviewerId` **一律硬编码 `'admin-1'`/`'system'`**；`recordAudit` 固定 `operatorName:'admin@shopro.ai'`、`role:'SUPER_ADMIN'`。⚠️ 迁移真后端必须以认证主体替换，否则审计日志操作人失真（安全/合规风险）。

## 七、切换到 Spring Boot REST API 的可行性结论

**总体判断：接口边界与数据模型足以支撑前端功能完整落地（可行性 中高），但存在 4 类必须先补齐的契约缺口。**

支撑点（已具备）：
1. 端点划分清晰、按域聚合（auth/dashboard/customers/credits/workflows/risk/billing/tickets/system），可作为 Controller/路由分组直接映射。
2. 统一响应包裹 `ApiResponse{code,message,data,traceId}` + 分页 `PageResult`，与 REST 约定天然契合。
3. 关键写操作已具备**幂等键**（credit-adjustment、entitlement-grant、refund、job-refund）与**状态守卫**（风险/退款/重试/取消的合法前置态），后端可据此实现乐观并发与业务校验。
4. 金额以最小货币单位整数建模、状态机枚举完备、审计与账本不可变理念已体现——数据模型层面可直接落库。

迁移必须处理（阻塞项）：
- **鉴权模型**（6.3）：以服务端签发 token + 会话校验替换 `x-shopro-admin-role` 客户端头与 localStorage 还原；`roleFromRequest` 缺省由 fail-open 改 fail-close。
- **端点级授权**（6.3）：为所有读接口与工单写接口补权限校验，形成与 `permissions.ts` 一致的服务端策略；权限码固化为共享契约（枚举/常量清单）。
- **状态码语义**（第六节 + 3.x）：当前业务/校验/未找到**统一返回 400 `VALIDATION_ERROR`**，未使用 `401/404/409/429` 与 `UNAUTHORIZED/NOT_FOUND/CONFLICT/IDEMPOTENCY_CONFLICT/BUSINESS_RULE_VIOLATION`（这些码在 `types/api.ts`、`error-codes.ts` 已定义却从不发出）。真后端应规范映射，前端 `client.ts` 已按 `status===401||code==='UNAUTHORIZED'` 广播未授权事件，需后端兑现。
- **异步副作用**（6.4）：重试/取消/退款执行由回调或服务端调度驱动，前端以轮询/SSE 取代 `setTimeout`。
- **聚合与连接字段**（3.4、6.5）：列表 DTO 需输出 join 派生字段；订单指标改后端聚合端点。
- **闭环补齐**（6.1、6.2）：新增审批通过/驳回与积分冲正端点。
